DISEÑO TÉCNICO · CONCEPTO

El Gerente IA del Hotel

Un sistema de agentes de IA que opera el hotel llamando a la misma API que un humano. Este documento explica cómo funciona por dentro: el loop del agente, las herramientas que usa, quién decide si ejecuta solo o pide permiso, y un trace real de qué hace paso a paso.

🔍 Observa
Lee el estado del hotel por la API.
🧠 Piensa
LLM con herramientas (function calling).
⚡ Actúa
Ejecuta llamadas HTTP con permisos.
🛡️ Verifica
Gatekeeper aprueba cada acción.
⚠️ El Gerente IA no es una terminal/CLI que escribe comandos. Tampoco toca la base de datos. Es un programa (worker) que habla con un LLM (Claude u otro), y el LLM decide qué herramientas ejecutar — y esas herramientas son llamadas HTTP a la API del propio sistema.

3 · Stack técnico — qué procesos corren

Esto NO vive dentro de un módulo del PMS. Es un servicio aparte que se conecta al PMS por su API. El propio sistema ya tiene las tablas ai_* y el permiso ai:edit: las reusamos.

🔁 Event Bus

El PMS publica eventos cuando algo pasa (reserva creada, factura vencida, limpieza lista). Implementación simple y portable: una tabla ai_events + un poller. Sin Redis obligatorio.

🤖 Agent Worker (Bun)

El programa principal. Consume eventos del bus, carga el agente que corresponde, corre el loop LLM↔tools, aplica el gatekeeper y escribe el trace en ai_runs.

🧠 LLM API

El cerebro. Claude (Anthropic) por defecto, con function calling: le pasamos las tools disponibles y decide cuál llamar. Por hotelería se prefiere Claude por razonamiento y baja alucinación.

🧰 Tool Layer

Wrappers que el worker ejecuta. Cada tool = una llamada HTTP a /api/* con el service token del agente. El PMS valida permisos como a cualquier usuario.

✋ Approval Queue

Tabla ai_approvals. Cuando una tool es de nivel sugerir/aprobar, no se ejecuta: se encola y se avisa al humano (panel + WhatsApp). El humano aprueba con 1 click.

📒 Audit + Trace

Cada tool ejecuida deja fila en audit_log con actor=ai:front-desk. Y cada corrida completa, su traza en ai_runs (prompt, tools llamadas, respuesta, costo).

4 · Cómo funciona por dentro: el loop del agente

Cada agente corre el mismo patrón: Observar → Pensar → Actuar → Verificar, en bucle, hasta que el LLM decide que terminó (o que necesita al humano). Esto se llama agentic loop con function calling.

1
👁️ OBSERVAR

Llega un evento (o un cron). El worker carga el contexto: la reserva, el hotel, la ocupación, historial. Todo por la API.

2
🧠 PENSAR

Se manda todo al LLM junto con el catálogo de tools disponibles. El LLM responde qué tool quiere usar y con qué parámetros.

3
⚡ ACTUAR

Antes de ejecutar, pasa el gatekeeper. Si pasa, el worker hace la llamada HTTP a la API. Si no, la bloquea o la encola.

4
✅ VERIFICAR

El resultado vuelve al LLM. Decide el próximo paso (volver a 2) o terminar. El loop sigue hasta end_turn.

📌 Por qué importa el bucle: el agente no decide todo de una. Da un paso, ve qué pasó, y recalcula. Si asignar la habitación falla (sin stock), lo ve y prueba otra cosa. Eso es lo que lo hace robusto, no un script rígido.

5 · Las herramientas de la IA — qué llama en concreto

Esto es lo central. Las "herramientas" del Gerente IA son los endpoints de tu propio sistema, envueltos como function-calling del LLM. Cada tool = una llamada HTTP con método, ruta, permiso y nivel de autonomía.

Una tool se declara así (JSON Schema que el LLM entiende):
{ "name": "assignRoom", "description": "Asignar una habitación disponible a una reserva", "input_schema": { "type": "object", "properties": { "reservationId": { "type": "string" }, "roomId": { "type": "string" } }, "required": ["reservationId", "roomId"] }, "x-backend": { "method": "POST", "path": "/api/reservas/{reservationId}/assign" } }

El LLM solo ve name, description e input_schema. El x-backend lo usa el worker para saber qué HTTP hacer. El LLM nunca arma la URL ni toca la DB.

6 · Cómo se ENTERA de las tareas

Tres fuentes, una arquitectura. Todo pasa por el Event Router, que decide qué agente despierta.

🚨

Eventos del PMS

El principal. Cuando el PMS hace algo importante, publica una fila en ai_events.

{ type: "reservation.created", hotelId, reservationId, at }
⏰

Cron / rutinas

El worker programa chequeos periódicos: no-shows nocturnos, cobros vencidos del día, cierre de caja.

nightly 03:00 → checkNoShows daily 22:00 → checkOverduePayments
📸

Snapshot (contexto)

No es una tarea, es el "foto del hotel" que el agente carga al arrancar para tener contexto fresco.

GET /api/dashboard → ocupación, ingresos, pendientes, alertas

7 · El gatekeeper — quién deja ejecutar cada acción

El LLM propone una tool. Antes de ejecutarla, el worker pasa por el gatekeeper. Es código determinista (no IA) que aplica reglas. La IA nunca se saltea el gatekeeper.

①
¿La tool está en el scope del agente?
Si el agente Front Desk propone un refund → fuera de scope → BLOQUEAR + alertar.
②
¿Está en la lista negra (guardrails)?
Ej: "nunca anular factura". Configurada por el admin. → BLOQUEAR.
③
¿Qué nivel tiene la tool?
read ejecuta · auto ejecuta · aprobar encola · sugerir solo propone.
④
¿Tope diario / costo?
Si el agente supera su cupo de acciones del día → pausar + avisar.
⑤
Registrar en audit
Pase o no pase, la decisión queda en audit_log con el porqué.
// pseudocódigo del gatekeeper — determinístico, no LLM function gate(agent, tool, input): if tool not in agent.scope: return DENY("fuera de scope") if tool in agent.guardrails: return DENY("prohibida por config") if agent.dailyQuotaSpent(): return PAUSE("tope diario") level = tool.level if level == "read" or level == "auto": return EXECUTE(...) if level == "aprobar": return ENQUEUE(approval) if level == "sugerir": return SUGGEST(approval)

8 · Los niveles de autonomía

💡 SUGERIR

riesgo alto

El IA propone. El humano decide.

→ anular factura · devolver dinero · cancelar reserva pagada

✅ APROBAR

riesgo medio

Prepara todo. El humano confirma con 1 click.

→ check-in · enviar mensaje · ajustar tarifa

🚀 AUTOMÁTICO

riesgo bajo

Hace solo, sin preguntar. Y registra.

→ asignar cuarto · generar código · leer estado
📈 Subís de nivel por confianza, no por fecha: semanas sin errores pasan de sugerir→aprobar; meses impecables, a auto. Finanzas se queda en sugerir mucho tiempo, y eso está bien.

9 · Identidad y seguridad técnica

🔑 Service token por agente

Cada agente es un "usuario" del PMS con su rol (ej. ai_front_desk) y permisos limitados. Cada llamada HTTP lleva:

Authorization: Bearer <service-token-front-desk> x-hotel-id: h_1 x-actor: ai:front-desk

🔒 El PMS valida igual que a un humano

Cada ruta ya tiene requirePermission(), ownership check y filtro por hotelId. El agente pasa por las mismas validaciones. No hay backdoor.

🏨 Multi-tenancy hard bound

El hotelId se inyecta en cada llamada. El agente del Hotel A jamás ve datos del Hotel B. Sin excepciones.

📒 Trazabilidad completa

Cada tool ejecuida → fila en audit_log con actor=ai:*. Cada corrida → ai_runs con prompt, tools, respuesta y costo en tokens. Si un huésped reclama, hay evidencia.

Reserva nueva por Booking a las 3:14 AM. Nadie trabaja. Así se ve la corrida del agente Front Desk, línea por línea — qué evento llega, qué piensa el LLM, qué tool ejecuta, qué devuelve, y dónde frena.

✅ Resultado a las 3 AM: el huésped ya tiene cuarto 204 y código 8421 sin que nadie se despierte. El dinero no se tocó: el link de seña espera al gerente. Y hay 4 filas de audit + 1 trace completo.
🛑 Y si el LLM se equivoca? El gatekeeper lo frena antes de causar daño. Ejemplo: si propusiera refundPayment (fuera de scope de Front Desk) → DENY, alerta al admin, y queda en audit. La IA propone; el código decide.

13 · Reglas de oro

1 · Permisos = contrato

El agente hereda un rol. No puede lo que ese rol no permite. El PMS valida igual que a un humano.

2 · Gatekeeper antes de cada tool

Código determinístico. La IA propone; el gatekeeper decide si ejecuta, encola o bloquea.

3 · Humano aprueba lo irreversible

Anular, devolver, cancelar pagado, fiscal → siempre nivel sugerir.

4 · Audit + trace siempre

audit_log por acción + ai_runs por corrida. Trazabilidad total.

5 · Event-driven, no polling

El sistema lo despierta. No revisa todo cada minuto.

6 · Multi-tenant hard bound + tope de costo

hotelId en cada llamada. Tope de acciones y tokens por agente/día.
